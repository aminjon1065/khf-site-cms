# Журнал решений — план работ КЧС (khf.tj)

Долгоживущие продуктовые/архитектурные решения, на которые план (`PROJECT_PLAN.md`) прямо ссылается требованием «записать в DECISIONS». В отличие от `PROGRESS.md` (хронологический журнал «что сделано по каждой задаче»), здесь — решения, сгруппированные по теме, без привязки к порядку выполнения плана.

## Пять статических страниц фронта (C-1)

Контекст: `leadership`, `structure`, `symbols`, `sos`, `sitemap` во фронте — не читают CMS, содержимое зашито в `app/[locale]/{route}/content.ts` (ru/tj/en). Все пять помечены комментарием «(заглушка CMS)», но эта пометка — единообразный шаблон по всем пяти файлам, а не дифференцированный сигнал: сама по себе она не говорит, какие из пяти реально нуждаются в переносе. Решение принято по содержимому каждой страницы, не по комментарию.

### Решение

| Страница | Итог | Обоснование |
|---|---|---|
| `leadership` | **Перенести в CMS**, отдельная сущность `Leader` (не `Page`) | `content.ts` содержит именные данные — ФИО, звание, срок полномочий, биографии председателя и замов (`app/[locale]/leadership/content.ts:57-70`). Это меняется при кадровых перестановках — событие непредсказуемое по времени и не совпадающее с циклом релизов фронта. Данные структурированы как повторяющиеся записи с одинаковыми полями (`photoLabel/role/name/bio` на каждого зама) — отдельная сущность с полями даёт редактору собственно редактируемые поля и порядок сортировки; общий `Page` с rich HTML потребовал бы от редактора вручную поддерживать разметку карточек и порядок — то, от чего план (C-1, вариант (а)) явно предупреждает («теряется специфичная вёрстка карточек руководства»). |
| `structure` | **Перенести в CMS**, отдельная сущность `StructureUnit` (+ поля-счётчики года образования/числа подразделений на уровне страницы) | Аналогично `leadership`: `units: StructureUnit[]` — повторяющиеся записи (`num/name/desc`) по специализированным подразделениям, плюс числовые плашки (`app/[locale]/structure/content.ts:65-68`, «68 подразделений по стране») — меняются при реорганизациях. Та же логика структурированных повторяющихся записей → отдельная сущность, не `Page`. |
| `symbols` | **Оставить статикой** | Государственный Флаг, Герб и Гимн Республики Таджикистан утверждены конкретными постановлениями с номерами и датами, прямо процитированными в тексте (`app/[locale]/symbols/content.ts:90` — «постановлением МН МО РТ от 14.03.2007, № 499» и т.д.). Изменение возможно только законодательным актом — редактируемость через CMS не даёт практической пользы, а создаёт риск случайного искажения официально утверждённого текста/символики без соответствующего правового основания. |
| `sos` | **Оставить статикой** | Лендинг мобильного приложения СОС — описание фич и ссылки на магазины приложений. Меняется вместе с релизами самого приложения (собственный цикл разработки/публикации), а не независимо от релизов фронта, поэтому «редактор меняет без релиза фронта» — не то преимущество, которое здесь применимо: обновление страницы и так требует координации с релизом приложения. |
| `sitemap` | **Оставить статикой** | `content.ts` собственным комментарием фиксирует инвариант: «все пути — через общий модуль `routes`, чтобы карта сайта не расходилась с реальной навигацией» (`app/[locale]/sitemap/content.ts:1-4`). Перенос в CMS сломал бы именно эту гарантию — редактируемый вручную список ссылок неизбежно разойдётся с реальной структурой маршрутов рано или поздно. Страница по своей природе производная от кода (`routes`), не редакционный контент.

Итог совпадает с рекомендацией плана (`PROJECT_PLAN.md`, C-1) — независимая проверка по фактическому содержимому каждого файла подтвердила её, а не просто скопировала.

### Реализация (не входит в C-1, заведено отдельными задачами)

Сама реализация (миграция `leadership`/`structure` в CMS: миграции БД, модели, admin-панель, API-эндпоинты, перевод фронта с `content.ts` на `fetch*`) — заведена отдельными задачами с оценкой (см. `PROGRESS.md`, будет закрываться отдельно от C-1):

- **C-1a. Перенести `leadership` в CMS** *(оценка: 4–6 ч)* — новая модель `Leader` (поля: `role`, `name` translatable, `bio` translatable, `photo`, `sort_order`, `is_chairman` bool или отдельная привязка «кто председатель»), миграция, фабрика, seeder на основе текущих данных из `content.ts`, admin CRUD (по образцу существующего модуля, например `Announcement`), публичный API-эндпоинт (`GET /api/v1/leadership`), перевод `app/[locale]/leadership/page.tsx` на `fetchLeadership()` вместо `getLeadership()`. Требует теста на публичный API и на сортировку/фильтрацию по локали.
- **C-1b. Перенести `structure` в CMS** *(оценка: 4–6 ч)* — аналогично C-1a: модель `StructureUnit` (`num`, `name`/`desc` translatable, `sort_order`), плюс решить отдельно, куда положить `stats` (год образования / число подразделений) — либо как поля настроек (`Settings`, уже существует под `fetchSettings`), либо как отдельные поля на самой сущности `StructureUnit` не подходят (это агрегаты, не свойства одной записи) — вероятно, `Settings`.

Обе — P2-класса задачи, не блокируют остальной план; взяты в работу по мере продвижения по backlog (после обязательных этапов C/D/E), не в рамках самого C-1.
